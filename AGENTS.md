# Инструкции по работе с LedgerFox

## Обзор проекта

- LedgerFox — Go-приложение (Go 1.27+): задача `lkdr` собирает чеки ФНС «Мои чеки онлайн» в SQLite, stdin-триггер даёт ручной запуск. Точка входа: `cmd/app/main.go`.
- Ключевые пакеты: `internal/jobs` (реестр задач + `lkdr`), `internal/triggers/stdin`, `internal/database` (GORM, только SQLite, запись через UPSERT), `internal/captcha` (RuCaptcha), `internal/mocklkdr` (мок API ФНС для тестов).
- Документация: `README.md` и `docs/` (`getting-started.md`, `configuration.md`, `development.md`, `lkdr-report.md`).
- Python-отчёты (`scripts/reports/*.py`) работают с SQLite-базой LKDR отдельно от Go-приложения; `make report` — интерактивное меню отчётов (раздел «Python-отчёты»).
- Сверять документацию с текущим кодом; не перезаписывать чужие правки.

## Архитектурные факты

- Конфигурация — библиотека confi: JSON-файл (`--config.file`) и CLI-флаги с теми же путями (`--stdin.user=all`), флаг перекрывает файл; неизвестные ключи/флаги и `--config.file` без расширения — ошибка на старте; есть `--help`.
- Поднимаются только модули с `enabled: true`; ошибка любого включённого модуля на старте — отказ с сообщением и кодом 1 (fail-fast); ни одного включённого модуля — тоже ошибка.
- Одна и та же job для одного пользователя не выполняется параллельно (`MultiMutex`); разные jobs и пользователи — параллельно. Идентификатор `all` у jobIDs запускает все jobs.
- Запуск только ручной: интерактивный stdin или однократный `--stdin.user=<id|all>` (`make parse` — `all`: все пользователи по алфавиту, ошибка одного не прерывает остальных, итоговый код 1). Планировщика нет — периодичность через внешний cron; SMS в фоне не спросить, авторизоваться заранее.
- Неофициальное API ФНС: изменения на стороне сервиса могут ломать сбор.
- Вывод: текстовый по умолчанию; `--json` — весь вывод построчным JSON (принудительно `log.encoding=json`); `--debug` — уровень DEBUG. В тексте задач результат включает пользователя: ` ✔ default/lkdr`.

## Команды разработки

- `make build` / `make bin` — сборка в `bin/` (`app`, `mocklkdr`); `make test` — `go test -v ./...` + автотесты Python-отчётов (`scripts/tests/`); одиночный тест: `go test -v ./path/to/pkg -run TestName`.
- Тесты: юнит-тесты colocated в пакетах (`internal/database`, `internal/common`, `internal/logs`, `internal/captcha`, `internal/jobs`, `internal/jobs/lkdr` + `storage_test.go`, `internal/jobs/lkdr/internal/{entities,loaders}`, `internal/triggers` + `internal/triggers/stdin`); интеграционные — `internal/jobs/lkdr/integration_test.go` (мок подменяет ФНС через redirect-транспорт; отдельно мок запускается `docker compose up mocklkdr` → `lkdr.apiUrl`); E2E — `cmd/app/e2e_test.go` (собирает бинарник и гоняет его как чёрный ящик). Новую логику сопровождать тестами.
- `scripts/dist.sh` — релизные архивы в `bin/` (кросс-сборка требует C-компилятор из-за SQLite/CGO).
- CI (`.github/workflows/ci.yml`): push в master / PR / workflow_dispatch, отмена устаревших прогонов; шаги — vet → `make bin` → `make test` → `go test -race ./...`; Go из go.mod, раннер ubuntu-latest. Dependabot: gomod ежедневно, PR авто-мерж кроме мажорных.

## Безопасность и приватность

- `config.json`, локальные БД (`*.db`) и отчёты (`reports/`, `lkdr-report.txt`) содержат персональные данные и секреты: не коммитить и не переносить содержимое в инструкции, коммиты и логи проверки. Все перечисленное уже в `.gitignore`.
- Не фиксировать в скриптах, правилах категорий, AI-промптах, тестах, примерах и документации репозитория ничего, что может указывать на конкретные личные покупки и операции: приёмы врачей, медикаменты, анализы и прочее, что пользователи не хотят видеть в отчётах. Маркеры категорий — только обобщённые основы слов (`лекар-`, `капл-`, `анализ-`), без названий конкретных препаратов, диагнозов и клиник из реальных баз. Если такое название нужно привести или вывести — использовать завуалированные обобщённые названия («аптечные товары», «медуслуги») или синтетические нейтральные примеры; в логах проверки реальные названия таких товаров не печатать. В отчётах товары приватных категорий (по умолчанию «Аптека и здоровье», `reports.privateCategories`) не выводятся построчно — видна только сумма по категории.

## Загрузка чеков

```bash
make parse
./bin/app --config.file=./config.json --stdin.user=all
```

- `internal/jobs/lkdr/job.go`: сначала загрузчик `Receipts`, затем `FiscalData`.
- `receipts.go`: инкремент от последнего `receive_date` телефона; первая синхронизация телефона — за 12 месяцев, настроек глубины нет (затея firstSyncFrom/firstSyncMonths/min-depth backfill откатана 2026-10-03: приводила к повторной перекачке окна при истории короче запрошенной; глубина истории в БД пользователя уже полная — 2023-10→2026-10); UPSERT чеков и брендов.
- `fiscal_data.go`: дозагрузка отсутствующих деталей и позиций; `receipt.fiscal.data.unavailable` — до 5 пропусков за запуск, следующий останавливает загрузчик; отсутствующие данные и известная внутренняя ошибка API пропускаются.
- `lkdr.maxRequests` (0 — без лимита; флаг `--lkdr.maxRequests=N`): максимум запросов выгрузки за запуск на загрузчик (страниц чеков / фискальных деталей). Остановка по лимиту — не ошибка. Живые проверки против реального ФНС делать с урезанным объёмом: `--lkdr.maxRequests=2 --lkdr.batchSize=10`.
- Отчёт сам не синхронизирует ФНС: для актуальных данных сначала запустить загрузку.

## Python-отчёты

Python 3.10+, только стандартная библиотека. Из корня репозитория:

```bash
python3 -m venv .venv
.venv/bin/python scripts/reports/lkdr_report.py --db lkdr.db --days 30 --top 10
PATH="$PWD/.venv/bin:$PATH" make lkdr-report
```

- Меню `make report` (`scripts/report.py`): автодискавери `scripts/reports/*.py`; id = имя файла; `_`-префикс — служебные, в меню не попадают; заголовок меню = первая строка docstring скрипта. Без меню: `./scripts/report.py <id> [args]`, `--list`. Без интерактива вообще: `make report-all` = ai-report (HTML месяца) + lkdr-report-ai (текстовый отчёт с AI-выводами и рекомендациями в консоль).
- Новые отчёты: копировать `scripts/reports/_template.py` (как добавлять — docs/development.md, раздел «Python-отчёты»); пример по правилам — `scripts/reports/example.py`. Автотесты отчётов — `scripts/tests/test_reports.py` (unittest; запускаются `make test` вместе с Go-тестами, поэтому `make test` требует python3).
- HTML-отчёт месяца: `make ai-report` → `scripts/reports/ai_report.py` рендерит шаблон `scripts/templates/lkdr-report.html` в `reports/lkdr-YYYY-MM.html` (месяц = конец периода: свежий чек или `--as-of`; перезапуск обновляет файл месяца; расчёты переиспользует `lkdr_report.py`). Отчёт собран из трёх частей-подотчётов с якорями `#part-*`: «Анализ» (AI-карточки, действия, сравнение периодов одной таблицей, категории + Прочее, магазины, повторные покупки), «Графики» (накопленные суммы двух периодов + столбики расходов по неделям `week-bar`), «Закупка на неделю» (ориентир и бакеты корзины, сезон месяца, таблица корзины, AI-план закупки). Дублирование визуализаций запрещено: одно число — одно представление (метрики-карточки + одна таблица сравнения; категории только полным списком `category-visual`). Повторяемые блоки шаблона обрамлены маркерами `<!-- block:name -->`…`<!-- /block:name -->` — правки вёрстки делать внутри блоков, сохраняя маркеры. AI вызывается дважды (JSON): карточки месяца (`build_ai_json_prompt`, схема lead/cards/actions) и план закупки (`build_shopping_prompt`, схема lead/groups/tips, `request_ai(..., required=…)`); агент — `ai.command` в config.json, по умолчанию codex; `--no-ai` отключить оба. Фолбэки — детерминированные `fallback_ai` / `fallback_shopping_ai`.
- ГОТОВЫЕ ОТЧЁТЫ НАПРЯМУЮ НЕ РЕДАКТИРОВАТЬ (постоянное указание пользователя от 2026-10-03): файлы `reports/*.html` и текстовые выгрузки генерируются — любая ручная правка будет затёрта при следующей генерации. Все изменения отчётов вносятся только через правки шаблона (`scripts/templates/lkdr-report.html`) и/или скриптов (`scripts/reports/*.py`) с обязательной перегенерацией (`make ai-report`, `make report-all`) и проверкой результата.

- Обязательные таблицы: `receipts`, `brands`, `fiscal_data`, `fiscal_data_items`; перед запуском проверять существование БД.
- Конец периода — `max(fiscal_data.date_time)` (переопределяется `--as-of`); текущий период сравнивается с предыдущим той же длины, обе границы включены.
- Расчёты: для положительных операций эффективный расход `max(total_sum - prepaid_sum, 0)`; `operation_type` 2 и 3 — отрицательные на полный `total_sum`; закрытия предоплаты не увеличивают расходы. Товарные суммы и количества — со знаком операции; товарная разбивка может расходиться с итогом чеков.
- Категории — `CATEGORY_RULES` по первому совпадению подстроки, без совпадения «Прочее»; в отчётах есть секция «Разбор Прочего» (топ позиций остатка + хвост одной строкой), чтобы остаток не был дырой в бюджете. Валюты: по умолчанию RUB, текстовые признаки Казахстана — KZT; не складываются. Приоритет переопределения: `--currency-receipt`, `--currency-store`, эвристика.
- Корзина продуктов на неделю (`--basket-days`, дефолт 180): регулярные продуктовые позиции (3+ чеков за окно), расход/нед и частота закупок по срокам годности — `SHELF_LIFE_DAYS` по категориям + `SHELF_LIFE_OVERRIDES` по ключевым словам (заморож-, зелень, яйц-, консерв-…); бакеты: каждую неделю / раз в 2-4 недели / запас впрок. Рекомендация «Брать» — за одну закупку, с округлением вверх до целой упаковки: шаг выводится из разовых покупок по чекам (`purchase_step`: все порции целые → 1; иначе НОД порций вида 0.9/1.8/2.7 → 0.9; плавающий вес → без шага), округление — `round_up_to_step`, метка вида «2×0.9 (~424 ₽)» — `BasketEntry.plan_qty_label` + `take_label` (в скобках — примерная стоимость закупки `plan_sum` по средней цене из чеков); «Как часто» — фактический интервал закупок `cadence_days` (окно / число чеков). Логика — `build_weekly_basket` в lkdr_report.py, используется обоими отчётами. Сезонность: `SEASONAL_PROFILES` (мороженое, прохладительные напитки, ягоды, горячие напитки, цитрусы — множители по месяцам, `seasonal_weight`, первое совпадение маркера) корректирует количество и сумму позиции корзины по месяцу конца периода (`BasketEntry.season_weight`, `adjusted_qty/adjusted_sum`; базовое среднее — `weekly_*`); сводка месяца — `seasonal_month_overrides`, метка — `seasonal_mark` (×1.6 / «—»). Колонка «Сезон» есть в обоих отчётах; сводка «Сезонность (месяц)» — над корзиной.
- Названия товаров при выводе (таблицы обоих отчётов, AI-промпты) сокращаются до `reports.maxItemNameChars` из config.json (по умолчанию 40, целое ≥ 1, иначе ошибка запуска; резолв — `_config.load_max_item_name_chars`); в текстовом отчёте тот же лимит действует и для магазинов, HTML-отчёт магазины не сокращает. Только отображение: агрегация и ключи — по полным названиям.
- Приватные категории: `reports.privateCategories` (по умолчанию `["Аптека и здоровье", "Косметика и гигиена"]`, пустой список отключает; резолв — `_config.load_private_categories`) — товары этих категорий не выводятся построчно в отчётах и не попадают в AI-промпты (включая корзину и план закупки), сумма видна только на уровне категории.
- Повторяющиеся покупки: положительный итог, количество > 1 и больше одного чека; сервисные строки исключаются по `SERVICE_ITEM_MARKERS`.
- AI-выводы (`--ai-summary`) вызывают внешний AI CLI — по умолчанию `codex exec --sandbox read-only`; агент настраивается `ai.command` в config.json (полная командная строка с аргументами, промпт — на stdin; резолв — `scripts/reports/_config.py::load_ai_command`, флаг `--ai-command` переопределяет). Таймаут 180 с на вызов, ошибка AI не ломает отчёт. В prompt — агрегаты и семейный контекст из локального `FAMILY.md` (без файла — фолбэк «2 взрослых и 2 подростка»); фолбэк и подстановка — `family_intro` в lkdr_report.py.
- Семейный контекст `FAMILY.md` (корень, персональные данные, в .gitignore; шаблон — `FAMILY.md.dist` в репозитории; резолв — `_config.load_family_context`): состав (взрослые/подростки/дети/питомцы), привычки питания, акценты отчётов. Создаётся и обновляется интервью с пользователем по просьбе («создай/обнови FAMILY.md»): задавать вопросы вариантами ответов (AskUserQuestion, multiSelect где уместно) с возможностью свободного ответа; структура — по .dist-шаблону. Содержимое файла не печатать в чат, логи и коммиты целиком.
- Шаблон-прототип HTML-отчёта: `scripts/templates/lkdr-report.html` — полный каркас (структура секций + стили) с плейсхолдерами `{{ … }}` и без реальных сумм и персональных данных; безопасен для коммита. HTML-отчёты и правки их вёрстки делать по этому шаблону; готовые отчёты с реальными данными — только в `reports/` (gitignored).
- Для проверки обычного отчёта достаточно запуска без AI с `--color never`; личные покупки не публиковать в логах. HTML-отчёт проверять без личных данных: `scripts/reports/_demo_db.py` (служебный, в меню не попадает) строит синтетическую демо-базу → `ai_report.py --db <demo> --out-dir /tmp/... --no-ai`; из неё же собран пример `docs/example-report.html` в README — после правок шаблона пример перегенерировать. Механическая валидация сгенерированного HTML: нет `{{`, нет `<!--`/`-->`, есть все части `#part-*`, заполнены новые блоки.

## Отчёты в AI-агенте (ZCode)

Инструкции агенту для работы с отчётами по просьбам пользователя:

- «Обнови HTML-отчёт» → `make ai-report` (перегенерирует `reports/lkdr-ГГГГ-ММ.html`, месяц — из данных; AI-агент из `ai.command`, при недоступности — карточки из данных).
- «Покажи/выведи отчёт здесь» → `make lkdr-report LKDR_FORMAT=md` — markdown-версия текстового отчёта (GFM-таблицы, `##`/`###`, без ANSI), заточенная под вывод прямо в чат: результат команды включить в ответ пользователю как есть, без кодового блока, чтобы таблицы отрисовались. Сузить объём: `LKDR_TOP=5`, `LKDR_DAYS=…`.
- «Всё сразу» → `make report-all` (HTML + текстовый отчёт с AI-выводами и рекомендациями в консоль).
- Выводить отчёт в чат — только по явной просьбе пользователя. Приватные категории скрыты по умолчанию (`reports.privateCategories`): названия их товаров нигде не печатать, включая чат; суммы — только на уровне категории.
